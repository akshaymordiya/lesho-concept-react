# 04 — API conventions

Every endpoint in `modules/` follows these rules. Read this once; the module files then only list what is specific.

## 1. Basics

- REST over HTTPS, JSON bodies, UTF-8.
- Base path `/v1`. Breaking changes go to `/v2`; additive changes do not bump the version.
- Three audiences share the API and are separated by token audience and path prefix:
  - Consumer: `/v1/...`
  - Merchant: `/v1/merchant/...` — every call is scoped to a business by the `X-Business-Id` header.
  - Admin: `/v1/admin/...`
- Field names are `camelCase`. Enums are lower `snake_case` strings.
- Timestamps are ISO-8601 UTC (`2026-11-14T12:30:00Z`). Dates are `YYYY-MM-DD`. Times of day are `HH:mm` in the branch timezone.
- Money is an integer in paise with the key suffix `Paise` when not obvious, or an object `{amount, currency}` in billing responses.
- Ids are opaque strings. Never parse them.

## 2. Authentication

```
Authorization: Bearer <access token>
```

- Access tokens are short-lived (15 minutes) and carry `sub`, `aud` (`consumer`, `merchant`, `admin`), `sid` (session), `exp`.
- Refresh with `POST /v1/auth/refresh`. Refresh tokens rotate on every use; reuse of an old one revokes the session.
- Public endpoints (browse, search, listing detail) accept anonymous calls. Anything that writes requires a token.

## 3. Standard headers

| Header | Direction | Purpose |
| --- | --- | --- |
| `Authorization` | request | Bearer token |
| `X-Business-Id` | request | Required on `/merchant/*` |
| `Idempotency-Key` | request | Required on POSTs marked *idempotent*. A UUID generated by the client per user action. |
| `X-Client` | request | `consumer-ios/1.4.0` etc. |
| `Accept-Language` | request | `en-IN` initially |
| `X-Request-Id` | response | Echo in bug reports and logs |
| `Date` | response | Used by clients to correct their clock for timers |
| `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` | response | Rate limit state |

## 4. Response envelope

Success, single resource:

```json
{ "data": { "id": "01J...", "...": "..." } }
```

Success, list:

```json
{
  "data": [ { "id": "01J..." } ],
  "page": { "nextCursor": "eyJ...", "hasMore": true }
}
```

Error:

```json
{
  "error": {
    "code": "claim_expired",
    "message": "This claim expired before it was used.",
    "details": { "expiresAt": "2026-11-14T13:00:00Z" },
    "fields": [ { "field": "startDate", "code": "unavailable", "message": "Not available on 2026-11-21." } ],
    "requestId": "req_01J..."
  }
}
```

`message` is safe to show to a user. `code` is stable and is what clients branch on. `fields` appears on validation errors.

## 5. Status codes

| Code | When |
| --- | --- |
| 200 | Read or update succeeded |
| 201 | Created. `Location` header points at the resource |
| 202 | Accepted for background processing (media) |
| 204 | Succeeded with no body (delete, mark read) |
| 400 | Malformed request |
| 401 | Missing or invalid token |
| 403 | Authenticated but not allowed |
| 404 | Not found, or hidden from this actor |
| 409 | State conflict: illegal transition, duplicate, date clash, limit reached |
| 410 | Resource expired (claim, story) |
| 422 | Validation failed; see `fields` |
| 429 | Rate limited |
| 5xx | Server fault; safe to retry idempotent calls |

## 6. Error codes (shared)

`unauthenticated`, `forbidden`, `not_found`, `validation_failed`, `rate_limited`, `idempotency_conflict` (same key, different body), `illegal_transition`, `consent_required`, `feature_not_in_plan`, `business_not_verified`, `content_link_required`, `duplicate_lead`, `offer_ended`, `claim_limit_reached`, `claim_expired`, `claim_already_redeemed`, `rental_dates_unavailable`, `rental_min_units`, `thread_closed`, `media_not_ready`.

## 7. Pagination, filtering, sorting

- Cursor pagination only: `?limit=20&cursor=<opaque>`. `limit` max 50.
- Filters are query parameters named after fields: `?categoryId=…&mode=rent&maxPricePaise=500000`.
- Sorting: `?sort=relevance|distance|price_asc|rating|recent`.
- Location context for discovery: `?areaId=…` or `?lat=…&lng=…`; plus `?radiusKm=5`.

## 8. Idempotency

POSTs that create a lead, claim, rental request, message, review or publish action are marked *idempotent* in the module files.

- The client sends `Idempotency-Key`. The server stores the key with a hash of the body and the response for 24 hours.
- Same key and same body: the stored response is returned, same status.
- Same key and different body: `409 idempotency_conflict`.
- Clients must reuse the key when retrying after a timeout and generate a new key for a new user action.

## 9. Concurrency

- State changes are verbs on the resource: `POST /merchant/leads/{id}/acknowledge`, not a free-form status patch.
- The server validates the transition; an illegal one returns `409 illegal_transition` with the current status in `details`.
- Editable resources return `version` (integer). Updates send `If-Match: <version>`; a mismatch returns `409`.

## 10. Rate limits (initial)

| Scope | Limit |
| --- | --- |
| OTP request | 3 per phone per 10 min, 10 per IP per hour |
| OTP verify | 5 attempts per challenge |
| Lead creation | 10 per user per hour, 3 per user per business per day |
| Claims | 20 per user per day |
| Messages | 30 per user per minute |
| Search and guide | 60 per user per minute |
| Everything else | 300 per user per minute |

## 11. Privacy rules in responses

- A business never receives a consumer's phone number unless the lead has a `share_phone` consent; even then it is returned only on the lead detail to members with access to that branch.
- Consumer responses never include another consumer's personal data. Review authors are shown as first name and last initial.
- `couponCode` is present only in responses to a user who holds an active claim on that offer.
- Merchant responses never include consumer browsing, saves or location.

## 12. Honesty fields

Any merchant-supplied fact comes with provenance so the client can label it:

```json
{
  "pricePaise": 485000,
  "provenance": { "source": "merchant", "updatedAt": "2026-11-12T09:00:00Z" }
}
```

`source` is `merchant`, `verified` or `system`. Clients render "merchant-provided · updated 2 days ago" from this, never from guesswork.

## 13. Real-time transport

- `POST /v1/realtime/token` → `{ "data": { "token": "…", "expiresAt": "…", "url": "wss://…" } }`.
- Connect, then send `{"op":"subscribe","channel":"user:self"}` or `thread:{id}` or `business:{id}`.
- Server frames: `{"channel":"thread:01J…","seq":42,"type":"message.created","data":{…},"at":"…"}`.
- On reconnect send `{"op":"resume","channel":"…","afterSeq":41}`. The server replies with missed frames or `{"type":"resync"}`, after which the client refetches over REST.
- Long-poll fallback for chat: `GET /v1/threads/{id}/messages?afterSeq=41&wait=25` holds up to 25 s and returns as soon as there is something new.

See `02-architecture.md` section B4 for which data uses which mechanism.

## 14. Media upload

1. `POST /v1/media` with `{kind, contentType, sizeBytes}` → `{mediaId, uploadUrl, headers}`.
2. Client `PUT`s the file to `uploadUrl`.
3. `POST /v1/media/{id}/complete` → `202`. Status moves `uploaded → processing → ready`.
4. Attach `mediaId` to a post, product or review. Publishing with media that is not `ready` returns `409 media_not_ready`.

Limits: images 10 MB (JPEG, PNG, WebP, HEIC); video 100 MB, 60 s, MP4 or MOV.

## 15. Documenting an endpoint

Module files use this shape:

```
### POST /v1/offers/{offerId}/claims        auth: consumer · idempotent
Request body, response body, errors, side effects (events, notifications).
```
